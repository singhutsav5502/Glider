Handoff

The handoff

One flag at the end of the message, naming the CLI you want. That is the entire syntax. It works from any of the three CLIs, to either of the other two.

fix the failing test in internal/foo /claude
refactor this module /agy
summarize the last ten commits /cursor-agent

You never leave your terminal

No second window, and no repeating the task. Glider runs the other CLI and puts its final answer into the session you are already in.

Its permission prompts reach you

Headless delegation normally forces you to switch permission prompts off. Glider does the opposite. It gives you the question with a token, and one reply grants exactly that one thing.

4472bef1 /claude:allow

The task arrives with context

The other CLI receives your task, the right directory, and your recent instructions. It starts informed, and it does not guess.

Why

Why run more than one

These are genuinely different tools, and that is exactly why they are better together.

  • STRENGTHS

    Each one is better at something

    One handles a long refactor well. Another is quicker on a small fix. Another reads an unfamiliar repository faster. Choose for each task, not once and forever.

  • BILLING

    You already pay for several

    An unused subscription is wasted money. Send work to the plan that still has room, instead of draining one quota while another stays full.

  • SAFETY

    Delegate without weakening permissions

    Handing a task to a headless CLI normally means switching its permission prompts off entirely. Glider relays every one of them to you, and grants them one at a time.

  • LOCK-IN

    A fourth CLI costs one YAML entry

    No code in the routing or delegation core checks which CLI is talking. Adding a tool means new files, never a rewrite. How that boundary works.

Access

Two ways in

You do not have to decide now. Start with the gateway, and switch to transparent mode later if a CLI ignores proxy settings.

Gateway

Point the CLI at Glider with one environment variable or one base-URL setting. Explicit, easy to reason about, and it works with every CLI.

http://127.0.0.1:8080/v1

Transparent

Glider redirects the outbound HTTPS of the CLI at the operating system level. Nothing to configure, and it works on a session that is already running.

This mode needs Administrator permission on Windows, or root permission on Linux. It selects the traffic by process name on the full machine. Read how interception operates before you turn it on.

Routing

Cheap turns never reach the cloud

A rename, an explanation, a format pass — none of these need a frontier model. Glider reads the rules from the top, and the first match sets the route. You can always override it by hand.

Install

Get it running

Pure local mode. No cloud key, and nothing leaves the machine. 

# 1 — the local model
ollama serve
ollama pull qwen2.5-coder:14b

# 2 — Glider
.\glider.exe --config configs\glider.local.yaml

# dashboard  http://127.0.0.1:8081
# gateway    http://127.0.0.1:8080/v1

Then point your CLI at the gateway — or turn on transparent mode and skip that step entirely. The full walkthrough.
