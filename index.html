5 000 ft

The handoff

Put the flag at the end of the message. The flag gives the name of the CLI that you want. This is the full syntax. It operates from each of the three CLIs, to each of the other two.

fix the failing test in internal/foo /claude
refactor this module /agy
summarize the last ten commits /cursor-agent

You stay in your terminal

You do not open a second window, and you do not write the task again. Glider runs the other CLI and puts its final answer in your session.

Permission questions come to you

When the other CLI stops for a permission, Glider gives you the question and a token. Reply with the token, and the run continues with that one permission.

4472bef1 /claude:allow

The task includes your context

The other CLI receives the task, the correct directory, and your recent instructions. It does not start with no data and then guess.

4 000 ft

Why you use more than one

The three CLIs are not equivalent. The differences are the reason to use them together.

  • STRENGTHS

    Each CLI is better at a different task

    One CLI is better at a large refactor. Another is better at a quick correction. Another is better when it must read an unknown repository. Select the CLI for each task.

  • BILLING

    You possibly pay for more than one

    A subscription that you do not use is a waste. Send the work to the plan that has capacity. Do not use all of one quota while another quota stays full.

  • SAFETY

    Delegation keeps the permissions

    Usually, to give a task to a CLI with no console, you must stop its permission questions. Glider sends each question to you, and you give one permission at a time.

  • LOCK-IN

    To add a fourth CLI is a small task

    You write one YAML entry and one adapter. No code in the routing or in the delegation examines the name of a CLI, and thus a new tool does not need a rewrite. How that boundary operates.

3 000 ft

Two ways in

You do not have to select now. Start with the gateway. Change to transparent mode later if a CLI ignores the proxy settings.

Gateway

Point the CLI at Glider with one environment variable or one base-URL setting. This mode is clear, and it operates with each CLI.

http://127.0.0.1:8080/v1

Transparent

Glider redirects the outbound HTTPS of the CLI in the operating system. You configure nothing, and it operates on a session that is already open.

This mode needs Administrator permission on Windows, or root permission on Linux. It selects the traffic by process name on the full machine. Read how interception operates before you turn it on.

It also uses your own machine

This is the other half of the work. A task that does not need a large cloud model can operate on your machine. Glider reads the rules from the top, and the first rule that agrees sets the route.

Start Glider

Use pure local mode. You do not need a cloud key, and no data goes off the machine. 

# 1 — the local model
ollama serve
ollama pull qwen2.5-coder:14b

# 2 — Glider
.\glider.exe --config configs\glider.local.yaml

# dashboard  http://127.0.0.1:8081
# gateway    http://127.0.0.1:8080/v1

Then point your CLI at the gateway. Or turn on transparent mode, and you do not do that step. The full procedure.
