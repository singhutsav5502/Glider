## The aim, stated precisely

A user drives **one** CLI — it could be `claude`, `cursor-agent`, or `agy`, whichever they already have installed and prefer, chosen for no reason more special than "that's what they typed" — and stays there for the whole session. Behind that single front door, Glider can transparently spin up **headless sessions of other agent CLIs** on the fly, hand them a sub-task, and fold the result back into the user's session so it reads as if the front CLI did it natively — right tool names, right diff shape, right streaming feel. **Native Glider Language (NGL)** is the pivot representation that makes this possible: every vendor's native event stream translates *into* NGL and *out of* NGL, and orchestration/routing/merging all happen in NGL terms, never in any one vendor's terms.

**NGL must be independent in the truest form: no vendor is privileged as "the" front.** Earlier drafts of this doc illustrated everything with `claude` as the front and modeled the delegation trigger on Claude's own `Agent` tool (§3) — that was an unexamined bias, not a design decision, and it quietly meant the design only worked symmetrically for two of the three vendors (see §3's rewrite below for why). Any of the three must be able to sit in front, and any of the three must be able to delegate to either of the others.

The routing half of this is not a new engine — `internal/orchestrator/pipeline.go`'s existing `DecideLocal`/`RoutingDecision` pattern (already how Glider decides local-vs-cloud today) extends cleanly to "which vendor" (§4), and — unlike a model-tool-triggered delegation — it doesn't care which CLI is in front, which is exactly why it's the mechanism this doc now treats as primary. The **execution** half — actually running a headless CLI session and feeding its output back — no longer has a ready-made primitive to reuse now that `internal/swarm` is gone; see §5.

## 1. NGL, named and versioned

Everything sketched as "Proposed common envelope" in `agent_cli_interop.md` — `Turn{Vendor, Raw, Parts}`, `Part{Kind, Text, ToolCall, ToolResult, ReasoningToken}`, `EditViews` (range-replace / hunks / unified-text / before-after + converter registry), vendor packs (YAML, hot-reloadable, tag-based, `unknown_tool_policy: passthrough`) — **is NGL**. This doc just gives it a name, a version, and a job beyond translation: orchestration.

- Package/namespace convention, matching how the vendors themselves name things (`agent.v1`, `aiserver.v1`, `exa.cortex_pb`): **`glider.native.v1`**.
- `glider.native.v1.Turn` is the unit that crosses every boundary in this doc: front adapter → orchestrator, orchestrator → delegate adapter, delegate adapter → orchestrator, orchestrator → front adapter.
- Versioned independently of Glider's binary release, same as the vendor packs — NGL growing a field to accommodate a 4th vendor's weird shape should not require every adapter to be redeployed in lockstep.

## 2. Two session-concurrency models, one interface

Live-traced flag support (this session, `--help` on all three):

| CLI | Persistent bidi stream? | Turn-by-turn resumption |
|---|---|---|
| `claude` | **Yes** — `-p --input-format stream-json --output-format stream-json`: keep the process alive, write NGL-derived JSON turns to its stdin, read NGL-derived JSON events from its stdout, indefinitely. |
| `cursor-agent` | No | `--resume [chatId]` / `--continue` / `resume` subcommand — each turn is a fresh process bound to a session id |
| `agy` | No | `-c`/`--continue` / `--conversation <id>` — same shape, fresh process per turn |

Two genuinely different transports need one contract so the orchestrator doesn't care which vendor it's talking to:

```go
// HeadlessSession is what the orchestrator drives. Two implementations, one contract.
type HeadlessSession interface {
    Send(ctx context.Context, turn glider.native.v1.Turn) (<-chan glider.native.v1.Turn, error)
    Close() error
}

// claudeBidiSession: one long-lived process, turn written to stdin, events read from stdout
// until the matching "result" event — Close() ends the process.

// resumeBasedSession (cursor-agent, agy): Send() spawns `vendor -p --resume <id> ...`
// per call (id empty on first Send, captured from that call's init event thereafter);
// Close() is a no-op, there's no process to hold open between turns.
```

This interface is the thing a vendor's adapter package implements; nothing above it (routing, merging, rendering-back) needs to know which of the two models is underneath.

## 3. Delegation is a `Part`, not a new concept — but it needs two independent triggers, not one

**Revised 2026-07-26 to remove a Claude-centric bias in the original draft.** The first version of this section modeled the delegation *trigger* entirely on Claude's own `Agent` tool — i.e., delegation happens because the front's model calls a subagent-shaped tool. That's a real, working mechanism for Claude (confirmed live) and Cursor (`task_tool_call`, `internal/cursorrpc/toolcall_map.go` wire field 19) — but Antigravity's live toolset is a narrow, self-declared subset of its wire-declared ~40-entry catalog (it told the model outright it has no delete tool and fell back to `run_command` rather than reach for a wire-declared `delete_file` — see `agent_cli_interop.md`), so a delegate-out tool for `agy` is unconfirmed and plausibly absent (§7). **A design that only lets a front delegate when its own model happens to expose a subagent tool is not front-independent — it silently privileges whichever vendors happen to have that tool.** Fixed by splitting into two paths:

### 3a. Primary path — interception-level delegation (front-agnostic, always available)

Glider decides, at the point it already intercepts/gateways a front's traffic (§4's `DecideVendor`), that a turn or sub-task should be fulfilled by a different vendor — the same mechanical point `DecideLocal` already picks local-vs-cloud today, before the front's own model has any say in it. This is **the required, load-bearing mechanism**, precisely because it never depends on the front's tool catalog: it works identically whether `agy`, `claude`, or `cursor-agent` is the front, including for a front with no subagent-tool concept at all. Its real dependency isn't the front's model — it's Glider being positioned in that front's traffic path in the first place (see the new prerequisite in §7: proven for Cursor via MITM today, unverified for Claude and `agy`).

### 3b. Optional path — model-initiated delegation via a native subagent tool

For fronts whose model *does* expose a subagent-shaped tool, that tool becomes a second, richer way to trigger the same underlying delegation — additive UX, never required, never assumed to exist. Claude's `Agent` tool is real, live-captured prior art for what this path can look like when available, and its shape is worth reusing as-is rather than inventing a new one:

- **Input**: `{description, prompt, subagent_type, run_in_background}` — `subagent_type` is exactly the `TargetVendor` slot, just scoped today to Claude's own agent profiles (`general-purpose`, `Explore`, `Plan`, …) instead of external CLIs.
- **Addressable, not fire-and-forget**: the subagent gets a persistent `agentId`, resumable later (`SendMessage`-shaped) — delegation is an async handle, not a blocking call.
- **Full async lifecycle already exists**: `task_started` → `task_progress` (periodic, carries `last_tool_name` + running token/tool stats) → `task_updated{status:completed}` → `task_notification` (summary + `output_file` pointing at the complete sub-transcript).
- **Correlation via `parent_tool_use_id`**, sharing the parent's `session_id` — not a separate session per subagent.
- **Return already carries budget/telemetry, not just a text result**: `{totalTokens, totalDurationMs, totalToolUseCount, resolvedModel, toolStats:{readCount, searchCount, bashCount, editFileCount, linesAdded, linesRemoved, otherToolCount}}`.

### The shared `Delegate` shape (both paths converge here)

Whichever path triggers it — Glider's own classifier (3a) or the front's model calling a subagent tool (3b) — delegation becomes the same NGL value:

```go
type Delegate struct {
    TargetVendor string            // "claude" | "cursor" | "agy" | "codex" (future) — or "" to mean "same as front, just a subagent"
    Task         string            // the sub-prompt / instruction
    ContextSlice []Part            // whatever the orchestrator decides the delegate needs — never the full transcript by default
    Workspace    string            // run-scoped path, see §5
    Budget       Budget            // timeout, max turns, max $ — delegating across a *paid* CLI needs an explicit ceiling, not "however long it takes"
    ReturnAs     string            // canonical tag the caller expects back: "edit" | "read_result" | "text" | ... (drives which EditViews conversion runs on return, see §6)
    Background   bool              // addressable/resumable handle instead of a blocking call
    TriggeredBy  string            // "interception" (3a) | "model_tool" (3b) — kept for audit/debugging, never changes downstream handling
}

type DelegateResult struct {
    AgentID    string    // persistent, resumable handle — mirrors Claude's real `agentId`
    Summary    string    // text result
    Stats      ToolStats // {TotalTokens, TotalDurationMs, TotalToolUseCount, ReadCount, EditCount, LinesAdded, LinesRemoved, ...} — lifted directly from Claude's real toolStats shape, generalized past "Claude-only" fields
    Transcript string    // pointer to the full sub-session record, not inlined by default
}
```

For path 3b specifically, a `Delegate` is just a `ToolCall` whose `tags` include `delegate` in the vendor pack sense from `agent_cli_interop.md` — the orchestrator recognizes it the same way it recognizes any other tagged tool call, no special-cased type. The practical implication: **the async lifecycle events (`task_started`/`task_progress`/`task_updated`/`task_notification`) are themselves worth adopting as NGL's delegation event vocabulary for both paths**, since one real vendor already validated that shape under real usage rather than it being a paper design — 3a delegations should be *observable* the same way, even though they're triggered differently.

## 4. Routing: extend `DecideLocal`, don't replace it — this is the primary delegation trigger (§3a)

`internal/orchestrator/pipeline.go`'s `PipelineCompleter.DecideLocal(r, req) (*backend.RoutingDecision, error)` already answers "local or cloud" per request using a classifier + sticky turn-family state (`routing.turn_family_ttl`, `docs/MITM_NETWORK.md` §Sticky `/cloud` turn family). The natural extension is a second decision, orthogonal to local/cloud: **which vendor**. This is the mechanism §3a calls "interception-level delegation" — it's not a secondary option, it's *the* thing that makes NGL work the same regardless of which CLI is in front, since it runs before the front's model is even involved.

```text
DecideLocal(req)   → local | cloud                          (existing)
DecideVendor(req)  → same-as-front | claude | cursor | agy | codex...   (new — same RoutingDecision shape)
```

Inputs to `DecideVendor` that already exist as data by this point in the design:
- The `Delegate.ReturnAs` tag and whatever capability tags the task implies (from vendor packs — e.g. "needs `browser`" narrows to whichever vendor's pack actually has a tool tagged `browser`; today that's `agy`'s wire-declared `open_browser_url`/`click_browser_pixel`/etc. cluster, *if* it turns out to be live and not another wire-declared-but-not-model-exposed case per `agent_cli_interop.md`'s correction — verify liveness before routing to a capability, don't trust the catalog alone).
- **Hosted-vs-local awareness, a real distinction now that Claude's `WebSearch` was confirmed to run server-side** (`agent_cli_interop.md`, distinct `srvtoolu_…` id): a capability tag backed only by a hosted tool is not a valid `DecideVendor` target in the "spin up a headless session" sense — there is no session to spin up, it's already remote. Vendor packs should mark hosted tools explicitly (`hosted: true`) so `DecideVendor` can tell "route the whole delegate to this vendor" apart from "this one capability happens to live on the vendor's servers regardless of which CLI asked for it."
- A live **capability probe** per vendor (§7) — no point routing to a vendor that isn't authenticated on this host.
- Ordinary routing concerns Glider already has: cost, latency budget, explicit user override (an NGL-level equivalent of the existing `/local` / `/cloud` sticky-force commands — e.g. `/agy`, `/cursor` as explicit per-turn vendor pins, same sticky-family mechanics).

Output is the same `RoutingDecision`/`ResolveBackendName`/`DecisionSummary` shape already threaded through `pipeline.go` — a vendor decision is not a new kind of thing in this codebase, just a new value in an existing dimension.

## 5. Execution — open again, needs a concrete design (was: reuse `swarm.WorkerFn`)

**This section is stale as of 2026-07-25 (later same day).** `internal/swarm` — including `WorkerFn`, `Runner`, and the whole fan-out/thread/weave machinery this section proposed reusing — was deleted in the v1 scope narrowing (CLI interop + routing/rulesets/analytics only; multi-agent swarm orchestration is explicitly out of scope now). What's still true: a headless CLI session, whatever drives it, is *a single bounded action that takes a prompt/context and returns a result* — that shape hasn't changed. What's gone is the ready-made scheduler/retry/concurrency-bounding harness (`swarm.Runner`) that used to sit underneath it for free.

What survives from the old design and should carry forward into the real design (next step, not done here):
- The function shape itself — `func(ctx, prompt/context) (result, error)` — is still the right unit; whatever replaces `WorkerFn` should keep that signature small and boring.
- `HeadlessSession` (§2) — persistent-stream vs. resume-by-id — is unaffected; that's about talking to the *vendor CLI*, not about how Glider schedules the call.
- `DecideVendor` (§4) is unaffected; picking a vendor and running one is a smaller problem than the swarm engine solved (concurrency bounding, multi-worker merge, wave sequencing) — a single delegate call may not need a "runner" at all, just a direct call from wherever the front adapter decided to delegate.

What needs a real answer instead of an assumption:
- **Who calls `HeadlessSession.Send()`?** Previously: `swarm.Runner.Run` via `WorkerFn`. Now: possibly `orchestrator.PipelineCompleter` directly (it already has `Executor`/`FanOutExecutor` as pluggable execution strategies — a delegate call could be a third strategy alongside single/fan-out), or a small new dedicated caller. This is the first thing the concrete system design (next step) should settle.
- **Concurrency/budget bounding for delegate calls** — `swarm.Runner`'s semaphore/inflight logic is gone; if a front session can have multiple delegates in flight, something needs to own that bound now.
- **Episode/result recording** — `WorkerFn` returned `contextkit.Episode` because that's what `swarm.Runner` merged; `contextkit` itself is untouched and still the right return shape, just no longer arriving via swarm's merge step.

### Workspace binding (reuses §5 of `agent_cli_interop.md`)

Every delegated session binds to Glider's existing run-scoped workspace root (`runs/<turn-id>/{work,out}`), never the vendor's own default. For `agy` specifically this means resolving/creating its explicit project binding (`--new-project` or `--project <id>`) *before* the first `Send()` — done once by the `agy` adapter, invisible to the orchestrator and the user. This was a real live-reproduced failure mode in `agent_cli_interop.md` (silent scratch-dir fallback → `invalid_args` tool error) and is exactly the kind of vendor quirk that must be absorbed at the adapter boundary, not leaked upward.

## 6. Rendering back: the front adapter is the only thing the user ever sees

This is the crux of "without losing out on usability and all expected features": **the front CLI's adapter is the sole renderer.** Whatever vendor actually executed a delegated task, the front adapter synthesizes an event in *its own* native shape from the NGL `Turn` that comes back — using exactly the `EditViews` converter registry and `Part` normalization already designed in `agent_cli_interop.md`. Concretely:

> User is in `claude` (front). A task gets routed to `agy` (§4) because it needs a capability only `agy`'s pack has. `agy` executes `replace_file_content` — the only edit shape it natively speaks is `{StartLine, EndLine, TargetContent, ReplacementContent}` (`agent_cli_interop.md` §Antigravity, live-decoded). That comes back as an NGL `Turn` with an `EditViews{RangeReplace: …}`. Before the `claude` front adapter renders anything, it asks the converter registry for `hunks` (with `Before` fetched from the workspace file if the registry doesn't already have it — `rangeReplaceToHunks` needs the pre-image). It gets hunks back, and *only then* emits a `stream-json` `assistant`/`tool_use{name:"Edit"}` + `user`/`tool_result{structuredPatch: […]}` pair — i.e., an event indistinguishable from `claude` having run its own `Edit` tool. The user never sees `agy`, `replace_file_content`, or a range-replace; they see an `Edit` diff, because that's the vocabulary the front they're sitting in speaks.

> Second, cheaper case, no converter needed: same setup, but `agy` executes `write_to_file` instead — `EditViews{WholeFile: {Content: …}}`. Claude's own `Write` tool already has a first-class "no diff, just a write" result shape (`structuredPatch:[]`, `originalFile:null`, per `agent_cli_interop.md`'s live capture) — so the front adapter doesn't need the converter registry at all here, it just emits `tool_use{name:"Write"}` directly from `WholeFile`. This is why `WholeFile` earned its own `EditViews` field instead of being forced through `RangeReplace`+full-file-as-one-giant-range or some other workaround: the *cheap*, lossless path only exists because the view matches what actually happened.

> Third, the reverse direction — proving this isn't Claude-shaped in disguise: user is in `agy` (front). A task gets routed to `claude` (§3a — `agy` has no §3b subagent tool, so this can *only* happen via interception-level delegation, which is exactly why §3a is required rather than optional). `claude` executes `Edit`, returning `structuredPatch` hunks natively — `EditViews{Hunks: […]}`. The `agy` front adapter has no `hunks` concept of its own; it asks the converter registry for `range_replace` instead (`agy`'s only native edit shapes are `RangeReplace` and `WholeFile`, per `agent_cli_interop.md`). A hunk-to-range-replace converter computes `{StartLine, EndLine, TargetContent, ReplacementContent}` from the hunk + pre-image, and the `agy` adapter renders it as a `replace_file_content`-shaped step, exactly as if `agy`'s own model had called that tool. The user in `agy` never sees `claude`, `Edit`, or a hunk — same guarantee as the first example, opposite direction.

Rules that fall out of this:
- **Raw is always kept, never shown by default.** `Turn.Raw` (the vendor's actual event) rides along for debugging/audit but the front adapter's default render path never surfaces it.
- **Unconvertible views degrade to a visible, honest fallback** — per `agent_cli_interop.md` §2 ("degrade explicitly, never silently guess"): if `hunks` genuinely can't be derived (no pre-image available, e.g. the delegate wrote to a file the front's workspace snapshot doesn't have), the front shows the vendor-native form directly (e.g. "range 10–12 replaced") rather than fabricating a fake diff. Silent-but-wrong is worse than honest-but-unfamiliar.
- **Large results go by reference, not inline, even across the vendor boundary.** `cursor-agent`'s `webSearchToolCall` already offloads big pages to a local file + pointer string rather than inlining them (`agent_cli_interop.md`) — NGL's `Part`/`ToolResult` should preserve that pattern universally: a delegate's large output becomes a workspace-relative pointer in the `Turn`, and the front adapter decides whether/how to surface or fetch it, rather than every adapter reinventing its own size limit.
- **Streaming granularity mismatch is a known, accepted seam.** `claude`'s front can stream token deltas; a resumption-based delegate (`cursor-agent`/`agy`) only returns whole turns per `Send()` call (§2). The front shows the delegate's sub-task as a single coarse-grained step — this is not a compromise invented for NGL, it's literally how `claude`'s own UI already renders its `Agent` (né `Task`) subagent calls today: one collapsible block with a summary + stats, not token-by-token (§3). Cross-vendor delegation should look exactly like same-vendor delegation already looks.

## 7. Operational prerequisites and honest limits

| Concern | Position |
|---|---|
| **Glider isn't in every front's traffic path yet — resolved to a decided architecture, not just de-risked** | §3a (the required, front-agnostic delegation path) only works where Glider actually intercepts/gateways the front's requests. Proven for Cursor via real MITM (`internal/mitm`, `docs/MITM_NETWORK.md`) since before this doc existed. Two things were tested live on 2026-07-26 to close the rest of this out: **(1) Claude Code's env-var override is real.** `ANTHROPIC_BASE_URL` fully redirected the actual `/v1/messages` completion call to a local test server — confirmed twice, once under `--bare`+`ANTHROPIC_API_KEY`, once under a normal OAuth session (real `sk-ant-oat01-…` bearer token observed in transit to our own localhost listener, immediately deleted from disk after capture — no credential persisted). A second test replayed that same real OAuth token through a naive reverse proxy to true `api.anthropic.com` and got a genuine `200 OK` with a correct model reply rendered by the CLI — so origin pass-through (§ auth, below) is not just theoretically fine, it's demonstrated end to end. Static analysis of the installed `claude.exe` backs this up structurally: it bundles undici's `EnvHttpProxyAgent`/`ProxyAgent` and literal `ANTHROPIC_BASE_URL`/`NODE_EXTRA_CA_CERTS` strings, so this isn't a fluke of one build. **(2) That mechanism was then deliberately rejected as the primary transport anyway.** An env var only takes effect at process launch — it cannot reach a `claude` session a user already has open in an existing terminal, and Glider's product requirement (stated directly, not inferred) is "run the exe once, forget about it," not "restart every open CLI session after installing Glider." That single UX constraint rules out env-var redirection as the default mechanism for any vendor, including ones where it works. **The replacement was then proven, not just proposed:** a WinDivert (`github.com/basil00/WinDivert`, v2.2.2) feasibility spike on this Windows 11 dev machine opened a sniff-mode handle (`WINDIVERT_FLAG_SNIFF \| WINDIVERT_FLAG_RECV_ONLY` — copy-and-observe, zero packets dropped, zero risk to real traffic) filtered to `outbound and tcp.DstPort == 443`, and in a 25s window captured 712 real TLS segments system-wide from processes that were already running before the driver loaded — including this very Claude Code CLI session's own traffic to Anthropic's real IP (`160.79.104.10:443`), interleaved with unrelated traffic from whatever else was talking on the box (Cloudflare/Google/Azure/AWS ranges). No env var, no proxy setting, no CLI cooperation, no relaunch. The machine already had one kernel packet driver loaded (Npcap's `npf`, for Wireshark) and was running elevated, so WinDivert's driver installed and later fully uninstalled (`sc delete`, confirmed gone) with no extra friction — a real signal this class of driver is viable on a normal dev Windows box, not just in theory. **Decided architecture:** OS-level, cooperation-free packet interception (WinDivert/WFP-callout-style: system-wide 443 watch, SNI-match against known vendor hosts, redirect matching connections into Glider's existing MITM decrypt/fulfill engine) is the primary, default transport for every vendor — including Claude Code. Env-var redirection (`ANTHROPIC_BASE_URL` and whatever equivalents future vendors expose) is kept only as an optional, explicitly-opt-in fast path for constrained environments (no admin rights, CI, containers) where installing a packet driver isn't possible — never the shipped default. The one-time cost that buys this is real and worth naming plainly: a signed driver install + CA trust, both admin-gated, both part of first-run setup — not per-session, not per-CLI-relaunch. |
| **Per-vendor transport is data, not a hardcoded choice — same pattern as `confirmed` in the vendor packs** | Not every vendor's completion plane needs the same transport tactic, and the vendor-pack design (`agent_cli_interop.md` §1) already has the right shape for this: add a `transport` field alongside `confirmed`/`tags` — `os_intercept` (default, no cooperation assumed) or `env_base_url` (opt-in fast path, only set `confirmed: true` after an actual live test proves the override reaches the completion plane, not just the docs/config plane — `cursor-agent`'s `--endpoint` is the cautionary example: it covers Dashboard/Config/Models/Analytics but was proven, via a mutex-fixed capture pass in `agent_cli_interop.md`, to **not** cover the actual completion call at all). `agy` has no CLI flag or app-level override, but turns out to be the *most* cooperative of the three vendors, not the least — fully confirmed on 2026-07-26, both halves. **Routing:** its Go-based HTTP client honors `HTTP_PROXY`/`HTTPS_PROXY` for its entire traffic, including the completion plane itself — a controlled tunneling proxy logged real `CONNECT daily-cloudcode-pa.googleapis.com:443` requests (not just the auxiliary `antigravity-unleash.goog`/`oauth2.googleapis.com`/`play.googleapis.com` hosts seen in an earlier pass) and `agy` completed its task normally (`pong`) end to end through it. **TLS trust:** a second pass replaced that tunnel with a proxy that terminates TLS itself for exactly `daily-cloudcode-pa.googleapis.com`, using a leaf freshly minted from Glider's own CA — four separate handshakes succeeded outright, with real decrypted request bodies read straight through (`POST /v1internal:loadCodeAssist`, `setUserSettings`, `listExperiments`, genuine production endpoints). No cooperation flag needed for either half — standard Go `net/http` proxy-env behavior plus a Go TLS stack that, like Claude Code's Node runtime, trusts the OS certificate store outright. (An earlier attempt at this same test mid-session tripped a real Google OAuth re-auth requirement — traced to a crude stub proxy that 502'd `oauth2.googleapis.com`'s `CONNECT`, not to anything about proxying itself; a clean run with real tunneling had no such issue.) So today: Claude Code and `agy` are both `confirmed: true` for env-based redirection *and* TLS-trust of a forged cert; only `cursor-agent` remains `os_intercept`-only — its completion plane is proven, not just unconfirmed, to ignore both `--endpoint` and standard proxy env vars (per `cursor-cli-proxy-fix`'s own finding). Three vendors tested now, zero certificate pinning found in any of them — worth remembering as a real, load-bearing data point, not an assumption, next time a fourth vendor needs the same two questions answered. |
| **Prior art for the process-level variant of this same idea, found searching for `cursor-agent`'s specific gap** | [`Mutual-Luo/cursor-cli-proxy-fix`](https://github.com/Mutual-Luo/cursor-cli-proxy-fix) documents the identical finding this doc already had from raw capture — `cursor-agent`'s real model-request path ignores shell-level `HTTP_PROXY`/`HTTPS_PROXY` — and works around it with **proxychains4**: a TCP-connect-level hook that wraps the *entire process*, intercepting every outbound connection regardless of protocol (plain HTTP, HTTP/2, gRPC, streaming), rather than patching one HTTP client's proxy config. That's the Linux/macOS-shaped version of exactly the OS-level thesis above — process-scoped instead of system-scoped, but the same "go below the app's own cooperation" idea. The Windows-shaped equivalent (connect-hook DLL injected into one target process, e.g. via Detours/MinHook — the same technique commercial tools like Proxifier use) is a narrower-blast-radius alternative to the system-wide WinDivert approach worth keeping in the design space: it only touches the one process being launched through Glider, at the cost of needing injection into (or a launcher wrapping) that specific process rather than a single system-wide watch. Not adopted over WinDivert here — flagged as the fallback shape if system-wide interception ever proves too broad a hammer for a given deployment. |
| **Scope decision (2026-07-26): build Windows first, but behind an interface Linux/macOS can satisfy without touching core** | Explicit product call — implement the OS-level redirector for Windows now; design it so a second OS is one new file, not a redesign, mirroring the exact "adapters are plugins, not core code" shape `agent_cli_interop.md` §4 already established for vendor packs. The seam: `TransparentRedirector` (`Start(ctx, listenPort, matchPorts)` / `Stop()` — get matching outbound traffic to a local port, however the OS does that) composed with `OriginResolver` (`ResolveOriginalDestination(conn) (host string, port int, err error)` — given an accepted, already-redirected connection, recover what the client actually meant to reach). Everything downstream of that interface is already OS-agnostic Go that exists today and needs **zero** changes: `internal/mitm/hosts.go`'s `matchHostPattern` and `internal/mitm/proxy.go`'s `mitmSession`/`blindTunnel` are the same host-allowlist-check-then-forge-leaf-or-tunnel logic `handleCONNECT` already uses for Cursor — a transparent ingress just needs one new function (peek the TLS ClientHello for SNI instead of reading `req.Host` off an HTTP CONNECT request, the way `handleCONNECT`, line 117–122, currently does) that resolves `host` and then calls into the exact same two functions. The redirector is a new front door, not a second engine. **Per-OS implementation, selected by Go build tag** (`_windows.go` / `_linux.go` — grepped the repo; no OS-specific build-tagged file exists yet, so this is a new pattern here, not an established one to follow): Windows uses WinDivert in active (non-sniff) mode — rewrite the matched packet's destination to `127.0.0.1:<transparent port>`, `WinDivertHelperCalcChecksums`, reinject — and because Windows has no OS-native "what was this redirected connection's original destination" lookup, the redirector itself must remember the 4-tuple → real-destination mapping in an in-process table at rewrite time and serve it to `OriginResolver`. Linux's future implementation is `iptables`/`nftables` NAT `REDIRECT` to the same local port, and its `OriginResolver` is materially simpler — `getsockopt(SOL_IP, SO_ORIGINAL_DST)` gets the original destination for free from the kernel, no bookkeeping needed. That Linux path is not yet proven, though: a same-day attempt inside WSL2 Ubuntu 24.04 (iptables installed cleanly, rule accepted, root available) produced no redirected connection at all — `lsmod`/`/proc/net/ip_tables_names` showed the stock `6.6.87.2-microsoft-standard-WSL2` kernel has no netfilter NAT modules compiled in, a known WSL2 limitation. The technique itself is industry-standard (it's what mitmproxy's own transparent mode and most corporate MITM appliances already run on real Linux), but confirming it here needs a real Linux host or cloud VM, not WSL2 — noted so a future attempt doesn't burn time rediscovering the same dead end. macOS has no live evidence either way (no Mac hardware in this session); the documented supported path is Apple's Network Extension framework (`NETransparentProxyProvider`/`NEFilterDataProvider`), with `pfctl` NAT `rdr` rules — already used by mitmproxy's and Charles's own macOS transparent-mode docs — as the lower-level fallback. |
| Auth | Delegating to a vendor requires that vendor already be authenticated on the host (OAuth/keyring/API key — all three use different stores). Glider does not manage third-party credentials; it **probes** (a vendor pack field, e.g. `probe: "agy models"` succeeding with exit 0 and non-empty stdout, mirroring how this doc's own research confirmed `agy` was already authenticated by running exactly that command) and only offers vendors that pass the probe as `DecideVendor` candidates. A vendor that isn't logged in is invisible to routing, not a hard error. |
| Cost/billing | One user action can now trigger spend against up to three separate subscriptions/API keys (Anthropic, Cursor, Google). This needs an explicit policy knob (e.g. `orchestration.cross_vendor_delegate: ask | auto | off`, defaulting to **ask** the first time a session would cross a vendor boundary, sticky per session after that) — silent cross-vendor spend is not acceptable default behavior. `Delegate.Budget` (§3) is the per-call ceiling; this is the session-level consent gate above it. |
| Concurrent workspace writes | A delegate and the front session can both hold a tool loop open against the same `runs/<turn-id>/work` tree. Needs the same kind of serialization Glider already needs for any concurrent tool execution (file-level locking or a single-writer-at-a-time rule per run) — not a new problem, but a real one, worth flagging rather than assuming away. |
| Antigravity likely has no delegate-out (§3b) primitive — **no longer a blocker** | Per §3 — still not directly confirmed (a spawn-and-wait-for-subtask probe wasn't specifically re-tested), and the evidence (agy self-reporting missing tools rather than reaching for wire-declared ones, `agent_cli_interop.md`) leans toward "consistent with a real limit." Now that delegation has two independent triggers (§3), this is no longer a design problem, just a capability gap: `agy` as a front simply never gets §3b's nicer model-initiated UX and relies on §3a for everything, same as any front would if a human explicitly typed `/cursor` or `/claude`. `agy` is a full peer as a **delegate target** either way, and still a full peer as a **front** via §3a alone. |
| `agy`'s wire-declared tool catalog is not its live toolset — this generalizes | The single biggest correction from the exhaustive pass: don't trust a vendor's binary-extracted or documented tool list as "what `DecideVendor` can route to." Every vendor pack needs a `confirmed: true/false` per tool (or per capability tag), set only by an actual live trace, and `DecideVendor`/tag-matching (§4) should weight `confirmed: true` capabilities over `confirmed: false` ones, or refuse to route to an unconfirmed one at all in a strict mode. This is not `agy`-specific — it's the honest default posture for any vendor pack going forward, including ones not yet captured. |
| Codex CLI (and future vendors) | By design (per `agent_cli_interop.md` §4 "adapters are plugins, not core code"), adding it is: one new vendor pack + one `HeadlessSession` implementation + one probe string. Nothing in §1–§6 above should need to change. This claim is untested until it's actually done once — the first non-Anthropic/Cursor/Google vendor added is the real test of whether the "no core changes" design goal holds. |

## 9. Context management across delegated sessions — open discussion, not a decision

Flagged explicitly as something to think through before `contextgraph` (`internal/contextgraph/`) gets a keep/cut/trim call, because delegation genuinely needs *some* answer to "what does the delegate know, and where does what it produced get recorded" — this can't be deferred as cleanly as "which UI package do we keep."

**What `contextgraph` actually is today**, from reading `graph.go`: an append-only `Store` of routing `Event`s, keyed to a `TurnView`, with exactly the machinery `StickyCloud`/`StickyLocal` turn-family behavior (`docs/MITM_NETWORK.md` §Sticky `/cloud` turn family) is built on — `BindRequest`/`BindSession`, `ResolveCloudSticky`, `RecentTurns`, `Export`. It is not a general knowledge base; it's **turn/session bookkeeping for routing decisions**, with local-disk persistence and pruning.

**Why this is directly load-bearing for NGL, not a separate concern:** a delegated sub-session (§3) needs exactly the same three things a StickyCloud turn family already needs — (1) a way to know "this delegate call belongs to that parent turn," (2) a way to re-resolve that binding on the *next* turn without re-deciding from scratch (the sticky-family TTL mechanic), (3) an export/audit trail. `Delegate`'s `AgentID`/`Transcript` fields (§3) and `contextgraph.TurnView`/`Export` are answering variants of the same question. Concretely, `ResolveCloudSticky(requestID, sessionKey) → (turnID, source, root, ok)` and a hypothetical `ResolveVendorSticky(requestID, sessionKey) → (turnID, vendor, agentID, ok)` are structurally the same function.

**Two ways this could go, laid out rather than decided:**

1. **Generalize `contextgraph` in place** — add `EventKind` values for delegate lifecycle (`EventDelegateStarted`, `EventDelegateCompleted`, …, mirroring the existing `EventRouteDecided`/`EventFulfilledLocal`), and a vendor-aware sticky resolver alongside (not replacing) `ResolveCloudSticky`. Cheapest option, reuses working persistence/pruning/export code, and keeps one place to look at "what happened in this turn" regardless of whether the answer is "routed cloud" or "delegated to agy." Risk: `contextgraph`'s current schema and naming (`RouteTallies`, `CloudTurnLive`) are fairly tightly local/cloud-shaped; bending it to also mean "which external CLI" may make both concerns harder to read.
2. **A separate, smaller delegation ledger**, purpose-built for `Delegate`/`DelegateResult` (§3), that only *references* a `contextgraph` turn id rather than living inside the same store. Cleaner separation, but two places to look, and reimplements sticky-TTL logic that already exists and works.

No recommendation forced here — but if pushed for a lean, the shared "sticky family" mechanic (point 2 above, "structurally the same function") is a real enough overlap that (1) is the shape it'd take if kept, and the decision is really just "is that overlap worth exploiting, or is it a coincidence that'll rot." Worth revisiting once real delegate traffic exists to look at, rather than deciding from the design doc alone.
