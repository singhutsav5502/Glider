Glider

Glider sits between your AI coding CLI and its backend. It can send a request to a local model instead of the cloud, and it lets you hand a task from the CLI you're in to a different CLI — with that CLI's permission prompts relayed back to you.

Step-by-step setup

What it does, concretely

Three things, in the order most people care about them:

  1. Delegate across CLIs. Type refactor this module /agy in Claude Code and Antigravity runs it. Works from any of the three CLIs, to any of the other two — you stay in one terminal. If the delegated CLI hits a permission wall, you get asked, right there in your own session. → Delegation
  2. Route work to a local model. Cheap, mechanical turns (rename, explain, format) can go to Ollama instead of burning cloud tokens, while architecture-shaped work stays on the real backend. You can always force it with /local or /cloud. → Routing
  3. See what's actually happening. Every intercepted request shows up in a local dashboard with its routing decision and why. → HTTP API

How it gets in the middle

Two ways, and you don't have to pick up front:

ModeWhat it needsBest for
Gateway Point the CLI at Glider (env var or a base-URL setting) Simple, explicit, easy to reason about
Transparent Nothing — Glider intercepts at the OS level CLIs that ignore proxy settings, and sessions already running

Transparent mode is genuinely zero-cooperation: it works on an already-open CLI session, because it redirects packets rather than asking the program to reconfigure itself. It needs Administrator (Windows) or root (Linux), and it is machine-wide by process name — read MITM & interception before turning it on.

Quick start

Pure local, no cloud keys needed:

ollama serve
.\glider.exe --config configs\glider.local.yaml

# Dashboard:  http://127.0.0.1:8081
# Gateway:    http://127.0.0.1:8080/v1

Then point your CLI at the gateway, or enable transparent mode to skip that step. Pure local has the full walkthrough.
