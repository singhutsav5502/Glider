Interop layer

NGL & interfaces

NGL (Native Glider Language) is internal/ngl's package of small, per-vendor interfaces that let claude, cursor-agent, and agy plug into Glider's shared code without that shared code ever branching on a vendor's literal name. Three interfaces, three different questions, three different directions of data flow — this page is the map between them, since it's easy to conflate "parse a vendor's own output" with "recognize a vendor's own request" the first time you're looking for where to add a fourth CLI.

Why three interfaces, not one

Each answers a genuinely different question, about data flowing in a different direction, at a different point in Glider's own pipeline:

InterfaceQuestion it answersData sourceDirection
OriginAdapter Is this HTTP request a vendor CLI's own live traffic to its own backend — and if I need to answer as if I were that backend, how? A live HTTP request Glider intercepted (MITM or gateway) Incoming — network → Glider
DelegateRenderer What did a headless delegate run actually print, cleaned up to just the final answer? A completed subprocess's captured stdout Outgoing (rendering) — subprocess → chat reply
ParseXTurn family
(ParseClaudeTurn, ParseCursorAgentTurn, ParseAgyTurn)		 What does one line of a vendor's own stream-json output mean, structurally — text, tool call, tool result, reasoning? One event line of a vendor's own headless/stream output Outgoing (structuring) — subprocess → Turn/Part

A fourth, separate interface lives one layer down in internal/vendors: VendorAdapter handles execution-time side effects (denial detection, session-id extraction, scoped permission retry via ExtraResumeArgs and/or GrantResumePermission, edit-view parsing, resume prompt framing) rather than wire-format parsing at all — see below for its full contract (and Delegation for the relay flow that calls through it). Don't confuse it with the three above; it's a different boundary (process execution, not wire format).

Turn & Part — the shared vocabulary

ParseXTurn functions all produce the same shape, defined once in turn.go: 

type Turn struct {
    Vendor string          // "claude" | "cursor-agent" | "agy" | future
    Raw    json.RawMessage // the adapter's native event, untouched
    Parts  []Part
}

Raw is always kept — normalization is additive, never a replacement, so a Turn can always be re-emitted to the same vendor untouched. Parts classifies content (PartUserText, PartToolCall, PartToolResult, PartReasoning, PartOther) without renaming anything — a ToolCall's Name/Args stay in the vendor's own vocabulary; a vendor pack's alias table maps names for callers that want cross-vendor uniformity, not this layer.

OriginAdapter — recognizing a front's own traffic

Built 2026-07-27 after a real, live bug: internal/mitm's delegate handler used to hardcode r.URL.Path != "/v1/messages" as its entry gate — true only when Claude Code is the front CLI. Typing a delegate flag directly into cursor-agent's or agy's own interactive session silently did nothing, because their own traffic is never Anthropic-Messages-API-shaped and the gate rejected the request before any flag-parsing logic ever ran. 

type OriginAdapter interface {
    Vendor() string
    Matches(r *http.Request) bool
    ExtractUserInstruction(body []byte) (text, model string, stream, ok bool, err error)
    // header is written immediately, before replyText resolves — keeps a
    // slow delegate call (headless run of another vendor's CLI) from
    // idling the client out, and names what was delegated to whom.
    WriteReply(w http.ResponseWriter, model string, stream bool, header string, replyText <-chan string) error
}

internal/mitm/delegate_handler.go calls ngl.ResolveOriginAdapter(r) and never compares a host or path against a vendor's literal name itself — each adapter's own Matches owns that. ExtractUserInstruction's ok=false is a distinct, deliberate outcome from a real error: it means the body parsed structurally fine but this adapter has no confirmed way to separate genuine human text from this vendor's own scaffolding — callers must fall through to real origin passthrough, never fall back to a raw substring scan. That exact shortcut, tried once for Claude before NGL existed, is what caused the original scaffold-injection bug this package's own doc comment describes.

VendorReal wire shapeConfidence
claudeAnthropic Messages API, POST /v1/messagesPublic spec — ground truth
agyGemini-style REST, POST .../v1internal:streamGenerateContent, human text wrapped in <USER_REQUEST> tagsLive-captured and byte-verified (2026-07-27)
cursor-agentConnect-RPC over genuine HTTP/2, POST /agent.v1.AgentService/RunLive-captured; request field path cross-verified against the public agent_v1.proto schema field-for-field

cursor-agent's completion host negotiates HTTP/2 unconditionally — invisible to any capture tooling (including, until 2026-07-28, Glider's own MITM proxy) that assumes HTTP/1.1. See MITM for the fix.

DelegateRenderer — clean replies, not raw transcripts

Built 2026-07-28: a headless delegate run's raw captured stdout is exactly what vendors.RunResult.Text holds — for claude and cursor-agent, that's the entire stream-json NDJSON transcript (every internal event line, not just the answer), because both vendors' headless mode is asked to emit it that way for denial/session-id extraction elsewhere in the pipeline. Relaying that whole blob as a delegate reply is exactly right for debugging and exactly wrong for daily use. 

type DelegateRenderer interface {
    Vendor() string
    Render(raw []byte) (clean string, ok bool)
}

claude's and cursor-agent's renderers both walk the NDJSON for the terminal {"type":"result","result":"..."} line — the vendor's own already-synthesized final answer, not a re-derivation — and use the last one found, same defensive "last, not first" choice LastUserInstruction makes for the incoming direction. agy's renderer is near-identity: agy has no --output-format flag at all, so its headless stdout is already plain prose. ok=false (no result event found, or an empty one) means fall back to the raw text — never guess a clean answer that might not be there.

vendors.ResolveDelegate renders through this by default (clean), controlled by a single Vendors-page toggle (Settings → Delegated task replies), not a per-message flag — an operator/debugging posture, not a per-task choice. Raw mode always shows the unformatted transcript; clean mode falls back to raw with a visible note when a renderer declines, so degraded formatting is never silently indistinguishable from a normal short answer.

VendorAdapter — execution-time side effects

Lives in internal/vendors/adapter.go, not internal/ngl — the single interface point every per-CLI quirk in the execution layer must go through. RunWithOptions and ResolveDelegate look up a VendorAdapter by vendor name and are otherwise blind to which CLI they're talking to; adding a fourth vendor, or changing how an existing one detects denials or grants resume permission, means writing or editing one adapter here, never branching on vendor.Name inside shared control flow. 

type VendorAdapter interface {
    // nil means "no denials found" — every adapter implements this, even a trivial no-op.
    DetectDenials(stdout, stderr []byte) []Denial
    // "" means none available (no such id in this vendor's format, or extraction failed).
    ExtractSessionID(stdout []byte) string
    // Scoped side effect OUTSIDE the resume argv itself; revert is always called after the
    // resume attempt, success or failure. cwd is the resolved workspace directory the resume
    // will run in (may be ""). Most vendors return a no-op revert — per-denial scoping happens
    // through ExtraResumeArgs instead (see below).
    GrantResumePermission(v Vendor, cwd string, denials []Denial) (revert func() error, err error)
    // Extra CLI args to append to the vendor's "resume" CommandTemplate for this specific set
    // of denials, or nil if the vendor has no such mechanism.
    ExtraResumeArgs(denials []Denial) []string
    // ok=false for a run that made no edit, or whose headless output carries no structured diff.
    ExtractEditViews(stdout []byte) (views ngl.EditViews, ok bool)
    // Lets a vendor reframe the resume prompt for its model's known behavior on a resumed call;
    // identity (returns prompt unchanged) for vendors whose resume already reliably completes.
    WrapResumePrompt(prompt string) string
}

Permission approval has to actually change something before a resume retry — otherwise the retried run hits the identical wall. Each CLI offers a different lever, which is why the interface has two grant methods for one concept: ExtraResumeArgs contributes command-line arguments scoped to the denied tool(s) (claude builds --allowedTools <comma-joined tool names> from the denials — the denied tool name is only known per-call, so it can't live in a static resume template), while GrantResumePermission performs a side effect outside the command line (agy writes a scoped rule into its own settings.json, then restores the original bytes afterward). A vendor implements whichever its CLI actually supports; shared code calls both and cares about neither. cursor-agent has no per-tool argv flag (only blunt -f/--yolo, deliberately never auto-used), so its adapter returns nil from ExtraResumeArgs and a no-op from GrantResumePermission — --resume [chatId] --trust alone suffices.

ExtractEditViews is the "show the file diffs through NGL" hook — it parses a completed run's raw stdout into canonical ngl.EditViews when the vendor's headless output carries enough structure. agy's headless mode is prose-only (no --output-format flag), so its adapter always returns ok=false here; that's an honest limit of the wire format, not a bug to paper over. WrapResumePrompt is a prompt-engineering mitigation for vendors whose resume reliably clears the permission gate but the model then describes the directory instead of acting (agy today) — not a guarantee, and distinct from either grant mechanism.

Unregistered vendor names fall back to noopAdapter — every method is a safe no-op, so callers never branch on "is there an adapter for this vendor" before calling one. The only place that lists all known vendor names for execution purposes is the vendorAdapters map in adapter.go.

Adding a fourth vendor

The point of all three interfaces: adding a vendor is new files, never a diff to shared dispatch code. A complete addition touches:

  • configs/vendor_candidates.yaml — probe args, print flag, default/resume/interactive templates (data, not Go).
  • internal/vendors/adapter.go — a VendorAdapter implementing all six methods (DetectDenials, ExtractSessionID, GrantResumePermission, ExtraResumeArgs, ExtractEditViews, WrapResumePrompt) for execution-layer behavior, not wire format — see VendorAdapter above.
  • internal/ngl/adapter_<vendor>.go — a ParseXTurn, if the vendor's own stdout needs structuring beyond plain text.
  • internal/ngl/adapter_<vendor>_origin.go — an OriginAdapter, only once its real live wire shape is confirmed — see the confidence column above; never registered on a guess.
  • internal/ngl/adapter_<vendor>_render.go — a DelegateRenderer, once its headless output shape is confirmed.

None of the five require touching internal/mitm/delegate_handler.go, vendors.ResolveDelegate, or any other shared dispatch code at all.
