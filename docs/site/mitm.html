Transparent redirection (Windows, WinDivert)

Cooperative MITM (proxy setting, CA trust) requires the CLI to be configured for it. Transparent mode removes that requirement entirely: Glider redirects outbound HTTPS on chosen ports for chosen process names at the OS packet level — no CLI cooperation, and it works retroactively on a session that was already running before Glider even started. 

mitm:
  transparent: true
  transparent_port: 8083
  transparent_ports: [443]
  windivert_dll_path: ~/.glider/mitm/windivert/WinDivert.dll   # WinDivertNN.sys alongside it

WinDivert rewrites a matched packet's destination to this machine's primary local IP on transparent_port (:8083 in the sample above — not loopback), recomputes checksums, and reinjects it — the client's own TCP stack never sees the rewrite. Windows has no OS-native "what was the original destination" lookup (unlike Linux's SO_ORIGINAL_DST), so the redirector keeps its own flow table keyed by the client's source ip:port. Process-name narrowing reads the same vendor registry the dashboard's Vendors tab populates — run discovery there first, or transparent mode has no process filter, only the port match.

Live-verified end-to-end for Claude Code (redirect + CA trust, zero cooperation, including an already-open terminal session). Not yet exercised the same way for cursor-agent/agy. Linux/macOS are designed (iptables REDIRECT + SO_ORIGINAL_DST; Network Extension / pfctl) but unbuilt.

Cursor's Agent RPC plane (BidiAppend → RunSSE)

Cursor's own wire protocol splits prompt and answer across two RPCs — this section and the two below are specific to Cursor's MITM plane, not a general mechanism.

  1. BidiAppend — prompt/context envelope arrives; latest-turn text extracted; decide → ArmLocal or ArmOrigin on the fulfill hub, keyed by request UUID.
  2. RunSSE — response stream opens; hub Wait(reqID, 800ms); local offer → encode text and fulfill; else dial origin.

Only root Agent RunSSE is a candidate for text-only local fulfill. Child/tool-loop RunSSE stays on origin by default (opt-in mitm.agent_rpc_tool_codec ships a common ToolCall map; the full catalog is still deferred) — use the gateway for Agent+tools.

Fulfill hub internals

AgentFulfillHub correlates BidiAppend (prompt) with RunSSE (answer) for the same request UUID, under one mutex: waiting (RunSSE arrived first), pending (Bidi arrived first), family (turn-family sticky state). ArmLocal/ArmOrigin signal a waiter if one exists, else store pending and schedule a 30s GC. Wait checks pending, else registers a waiter and selects on offer vs. an 800ms timer — on timeout it re-checks pending once, for the race where Bidi lands exactly as the timer fires. A local-fulfill encode failure after a partial write must not dial origin — the client already consumed a response.

Sticky-cloud state machine

Turn-family sticky is not conversation-wide. An explicit flag or a cloud DecideLocal decision opens a short-lived family keyed by the root request UUID; immediate chrome follow-ons (reply summary, title gen) inherit it. Without this, those follow-ons look like small local prompts and steal turns that must stay on the cloud parent that just ran.
