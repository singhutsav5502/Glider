Hoops

Loop Engineering

Per Addy Osmani and cobusgreyling: you design a system that prompts agents — observe → plan → act → evaluate → learn — not a one-shot prompt, and not Cursor IDE /loop cron as the product definition.

Glider hoop cycle

Memory → Router → Planner → Actor → Critic (eval 0–1) → Learn → Memory
         └─ stop on goal / score / max iterations / human gate

Hot-swappable stages

StageRole
routerPick local / cloud / auto for following stages
plannerDiscover / triage / decompose
contextSeed shared contextgraph (RecordHoopContext) → later stages see [context_digest]
actorProduce the artifact (optional parallel + parallel_mode)
criticMaker ≠ checker — score “done”
memoryLoad/persist (contextgraph + hoop state)

Human gate (HITL) & on_fail_n

human_gate: true
eval:
  goal: Critic score meets bar
  min_score: 0.7
  on_fail_n: 3   # stop after N consecutive critic fails (no infinite HITL reopen)

When paused, the gate payload includes ask (critic / actor / plan excerpts). Resume from the dashboard or:

POST /api/loops/{id}/approve
{}
POST /api/loops/{id}/resume

Parallel fanout vs nested swarm

- id: workers
  kind: actor
  parallel: 3
  parallel_mode: fanout   # default — CritiqueMerge workers
  # parallel_mode: swarm  # nests swarm.Runner (sample: parallel-swarm-mode.yaml)
  roles: [quality, security, secrets]

fanout = mid-cycle swarm.FanOut + merge. swarm = Phase 1 nested Runner.Run / RunWaves (requires orchestration.swarm.enabled; no silent fallback).

Skills (SKILL.md)

skill: security-audit          # → skills/security-audit/SKILL.md
skill: skills/audit/SKILL.md   # explicit path
skill: "Always cite file paths"  # plain string fallback

Search roots: orchestration.loops.skills_dir, tools workspace, then process cwd. Loaded file body is injected as [skill]; unresolved refs keep the string as [skill: …].

Parallel worker isolation (worktrees MVP)

orchestration:
  loops:
    worktrees: true   # default false

When enabled and a stage has parallel > 1, each worker gets runs/<hoop-id>/work/wN/. If the tools workspace is a git repo, Glider tries git worktree add --detach; otherwise it creates plain subdirs. Workers see a WORKER_ROOT prompt hint. Shared tools registry is unchanged — isolation is path convention + optional git worktrees. Config key ships in configs/glider*.yaml.

Feeds edges (data seed)

graph_edges:
  - { id: feed1, source: producer, target: consumer, kind: feeds }
  # alternate: kind: flow, label: feeds

Feeds are data-only (not control-flow): when the producer stage finishes, its summary is upserted into contextgraph (feed_<stageId> + RelFeeds). The consumer prompt gets a FEEDS: block with that summary and artifact paths. SM WalkOrder skips feeds edges. Sample: samples/hoops/feeds-edge-mvp.yaml. Cross-hoop / Temporal-class feeds remain deferred.

Per-stage autonomy / human_gate

autonomy: L3
stages:
  - id: risky
    kind: actor
    autonomy: L1          # gate before this stage on an L3 hoop
    # human_gate: true    # same effect without changing autonomy
  - id: critic
    kind: critic

Hoop-level human_gate / L1 critic-fail HITL still works. Stage fields add gates without a kind: human_gate node.

Feeds edges (data seed)

graph_edges:
  - { source: research, target: synth, kind: flow }     # control
  - { source: research, target: synth, kind: feeds }    # data only
  # alternate: kind: flow + label: feeds

kind: feeds is not control-flow (skipped by SM WalkOrder). When the producer finishes, its summary is upserted (feed_<stageId>) and the consumer prompt gets a FEEDS: block. Sample: samples/hoops/feeds-edge-mvp.yaml. Cross-hoop / Temporal feeds topology is DEFERRED (in-hoop MVP only).

User guide: Hoops, Graph, Swarm

Two related but separate surfaces share state with the Hoops tab: the stage graph (hoop pipeline) and the swarm thread graph (one-shot orchestrator fan-out). Agent logs are per-instance, never a mixed global stream.

Hoop (loop cycle)

  1. Open Graph editor → Stage graph. Add stages from the palette (or + Code stage for custom id/prompt).
  2. Edit a stage to bind MCP servers / tools (or builtins via Tools JSON). Manage connections on the dashboard MCP tab — see Tools & MCP.
  3. Turn on Link mode, drag node-to-node for flow edges. Double-click an edge (or Edge type) to toggle flow vs feedback. Use Fit / wheel zoom; pan on empty canvas.
  4. Back on Hoops & Swarm: set name, goal, route (default local), Create hoop.
  5. Click the hoop card so Agent log shows Following hoop <id>, then Start. Cycle: Memory → Router → Planner → Actor → Critic (stop on goal / score / max iterations).
  6. Edit graph on the card reloads stages into the shared canvas for Update.

Swarm (dashboard Run swarm)

  1. On Graph editor → Swarm thread graph: Add thread roles, Link mode to connect orchestrator ↔ workers. Only linked roles sync into the Roles field.
  2. On Hoops → Swarm wave: prompt + max workers → Run swarm.
  3. Server path: POST /api/swarm/run → swarm.Runner → FanOut (bounded workers, parent cancel) → MergeResults. UI paints ok/fail on worker nodes and binds Agent log to the run turn_id.

Fan-out inside a hoop

If an actor (or similar) stage has parallel: 2+ (optional roles), default parallel_mode: fanout calls swarm.FanOut mid-cycle and critique-merges workers before Critic. Set parallel_mode: swarm to nest a full swarm.Runner instead (see samples/hoops/parallel-swarm-mode.yaml). Gateway prompts with /swarm or [fanout] use orchestration.fan_out when enabled.

Graph-first compose

Dashboard Graph editor uses Cytoscape.js 3.30.4 (MIT, vendored under internal/dashboard/static/vendor/) with cytoscape-edgehandles 4.0.1 for drawable / reconnectable edges. Stage nodes use Loop API kinds (router / planner / actor / critic / memory); + Code stage opens a dialog for custom id, name, prompt, route, and critic eval_min on those kinds. Swarm is an orchestrator plus worker threads. Edit on the canvas: Link mode + drag to create or reconnect edges, Delete to remove, double-click an edge (or Edge type) to toggle flow vs feedback. Pipeline order for POST/PUT /api/loops is derived from flow edges into #hoop-stages-json; graph_edges are persisted on the hoop so topology reloads. Swarm roles sync from linked threads. Hoops "Open graph editor" / Edit graph shares that state with Create / Update / Start / Stop.

Per-instance agent logs: each hoop id and each swarm run id has its own ring buffer (not a global mixed stream). Click a hoop card or run a swarm to bind the Agent log panel (badge: Following hoop X / swarm Y). Rows are time | level | stage/role | message. GET /api/agent-logs?scope=hoop|swarm&id=...; WebSocket type=agent_log carries scope + instance_id. Starting a hoop or swarm resets that instance timeline.

Parallel actors: set parallel: 2+ (and optional roles) on an actor stage — the runtime fans out via swarm.FanOut and critique-merges workers before the critic. Live mid-cycle progress (phase / stage) is polled on hoop cards and paints the graph. Gateway sample: include /swarm or [fanout] in a prompt when orchestration.fan_out.enabled is on (scripts/examples/fanout_dual_view.star / fan_out_sample.star).

Run swarm paints live ok/fail on worker nodes. Inspired by Slate's orchestrator/thread model (randomlabs.ai/blog/slate), not a full thread-weaving UI.

Cutoffs: context vs max_tokens vs Glider caps

Mid-sentence logs (tool JSON, merge text, actor/critic) can be: (1) model num_ctx exhausted, (2) completion max_tokens / Ollama num_predict too low, or (3) Glider storage/prompt caps. Hoop Completes default to thresholds.default_max_tokens: 8192. Raise it for long audits; keep model max_context (e.g. 32768 for qwen 14b) above prompt+tools size. Dashboard Full output / Copy logs use stored attrs.text and stage outcomes (tens of KB), not the short log row. See planning/tools_mcp.md § Context window vs Glider truncate.
