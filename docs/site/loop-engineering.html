Loop Engineering

Per Addy Osmani and cobusgreyling: you design a system that prompts agents — observe → plan → act → evaluate → learn — not a one-shot prompt, and not Cursor IDE /loop cron as the product definition.

Glider hoop cycle

Memory → Router → Planner → Actor → Critic (eval 0–1) → Learn → Memory
         └─ stop on goal / score / max iterations / human gate

Hot-swappable stages

StageRole
routerPick local / cloud / auto for following stages
plannerDiscover / triage / decompose
actorProduce the artifact
criticMaker ≠ checker — score “done”
memoryLoad/persist (contextgraph + hoop state)

UI

Dashboard → Hoops & Swarm (http://127.0.0.1:8081): compose goal, stages, self-learning, route=local, Start.

Graph-first compose

Dashboard Graph editor uses Cytoscape.js 3.30.4 (MIT, vendored under internal/dashboard/static/vendor/) with cytoscape-edgehandles 4.0.1 for drawable / reconnectable edges. Stage nodes use Loop API kinds (router / planner / actor / critic / memory); + Code stage opens a dialog for custom id, name, prompt, route, and critic eval_min on those kinds. Swarm is an orchestrator plus worker threads. Edit on the canvas: Link mode + drag to create or reconnect edges, Delete to remove, double-click an edge (or Edge type) to toggle flow vs feedback. Pipeline order for POST/PUT /api/loops is derived from flow edges into #hoop-stages-json; swarm roles sync from linked threads. Hoops "Open graph editor" / Edit graph shares that state with Create / Update / Start / Stop.

Run swarm paints live ok/fail on worker nodes. Inspired by Slate's orchestrator/thread model (randomlabs.ai/blog/slate), not a full thread-weaving UI.
