Cross-CLI

Delegation & permission relay

Send a prompt from whichever CLI you're sitting in to a different installed CLI. Glider runs it headless, and if it pauses on a permission decision, relays that decision back to you as a normal reply instead of it silently auto-denying.

The flag

fix the failing test in internal/foo /claude
refactor this function /cursor-agent
summarize recent commits /agy

vendors.ParseDelegateCommand looks for a /vendor-name flag at the end of the message — never the start, never buried mid-sentence — claimed by DelegateHandler (or the gateway's own Messages route) before normal routing, so it never interferes with ordinary requests. A :template suffix picks a non-default command template, e.g. fix the auth bug /agy:interactive — every vendor ships an interactive template out of the box (configs/vendor_candidates.yaml): instead of running headless and relaying captured text back, it opens the vendor's own native session in a brand-new console window, already primed with your task as its first message, and hands control to you directly there. No output comes back into this chat.

Why the end, not the start: confirmed live, Claude Code's own client reads an unrecognized leading /word as a local slash command and never sends the message over the network at all ("Unknown command: /agy"). A flag typed as your first characters never reaches Glider from that front — full stop, regardless of how Glider's parser searches. Trailing-only sidesteps this for every front, not just Claude Code. It also means the text before the flag survives intact as the prompt, instead of an earlier "search anywhere" version of the parser silently dropping whatever came before the first match.

Why this isn't just a live pause

None of the three supported vendors actually block for a permission decision in headless (-p) mode:

VendorHeadless permission behavior
cursor-agentNever blocks — a denial resolves inline in the stream-json output and the model continues
claude (Claude Code)Never blocks — denied tool gets an immediate error result; the terminal event carries a structured denial list
agy (Antigravity)Fails closed unconditionally — its own stderr says headless mode cannot prompt

So the real feature is a resume loop: run headless, detect the denial from already-captured output, ask you out-of-band, then resume the delegate's session with expanded permission once you answer. Not truly live — the run has already ended by the time the question is asked — but fast enough to feel responsive.

Granting permission (vendor-specific, hidden behind one interface)

Approving a denial has to actually change something before the retry — otherwise the resumed run hits the identical wall. Each CLI offers a different lever, so there are two ways to pull one:

VendorWhat approval actually does
claude Appends --allowedTools <denied tools> to the resume call. The tool name is only known per-call, so it can't live in a static template — it's built from the denial itself.
cursor-agent Nothing extra — --resume [chatId] --trust is sufficient on its own. Note it exposes no per-tool flag; the only alternative is --force/--yolo, which allows everything, so Glider deliberately never reaches for it on your behalf.
agy Writes a scoped rule into its own settings.json (plus the per-project config when the workspace matches one), then restores both files to their exact original bytes afterward. This is agy's officially-designed headless-permission mechanism, confirmed via its changelog — not a workaround.

That split is why the interface has two grant methods rather than one: ExtraResumeArgs contributes command-line arguments, while GrantResumePermission performs a side effect outside the command line. A vendor implements whichever its CLI actually supports; shared code calls both and cares about neither.

Two alternatives were tried and rejected for agy first: a plain --dangerously-skip-permissions resume flag looked cleaner (uniform with the other two) but proved unreliable live — the model responds by explaining the flag instead of acting on it. --continue/--conversation <id> alone also proved unreliable, resuming an unrelated "most recent" conversation instead of the denied one.

Every vendor's quirk sits behind one VendorAdapter interface (DetectDenials, ExtractSessionID, GrantResumePermission, ExtraResumeArgs, WrapResumePrompt, ExtractEditViews) — shared code never branches on a vendor name.

Workspace scoping

No wire protocol Glider intercepts carries a filesystem path, so a delegate call can't know the origin CLI's project directory from the request alone. Reading it from the origin process's memory (its PEB) was tried and rejected — Windows Defender's real-time cross-process memory-read protection silently truncates the read on a normal install.

Instead: the origin process's PID (resolved from the TCP connection, no memory read) keys a small directory registry. An unrecognized PID is asked once (<path> /workspace — same trailing-flag convention as above) and remembered for that process's lifetime; the dashboard's Vendors tab can set a default workspace to skip asking in the common single-project case.

Session context for the delegate

A delegated CLI used to receive exactly two things — the prompt text and a working directory — so it had no idea what the larger task was or which CLI asked. Now every delegate run gets its own private directory under ~/.glider/delegates/<id> holding a single context file, handed to the CLI through a flag that vendor already supports, so it's ingested during normal session startup rather than spent out of the prompt budget.

VendorHow the context reaches it
claude--append-system-prompt-file=<file> — the file's path is passed explicitly, so its name doesn't matter
cursor-agent--add-dir=<dir> — reads an AGENTS.md written inside that directory
agy--add-dir=<dir> — same convention, also AGENTS.md

Those flags are ordinary template args in configs/vendor_candidates.yaml ({{context_file}}, {{context_dir}}), so which flag a vendor needs stays data rather than a vendor-name branch in shared code. A vendor with no context configured simply runs without one — the flag is dropped rather than left dangling.

The file itself carries the task restated, which CLI delegated it, the workspace, and up to 6 recent human instructions from the calling session (oldest first, marked as background only).

Nothing is written into files you own. Your project's CLAUDE.md or AGENTS.md is never touched — an earlier design appended to them and had to lock, restore byte-for-byte, and self-heal after crashed runs. A per-delegate directory removes all of that: it belongs to exactly one run, and it's deleted when that run ends.

Rendering the result back

A delegate's edit is rendered as a diff appended to the reply regardless of which vendor produced it — VendorAdapter.ExtractEditViews parses the vendor's own edit shape (Claude's structured patch hunks, cursor-agent's before/after diff string, agy's range-replace or whole-file write) into a canonical EditViews that FormatEditSummary renders uniformly.

Known gaps

  • agy sometimes still asks a clarifying question after a successful grant instead of acting — ordinary agent caution on a one-shot destructive request, not a bug, but it means the loop isn't always one round trip.
  • No real interactive/pty relay (Path B). A genuinely live mid-execution pause — catching a TUI prompt inside an already-running headless call — would need Windows ConPTY plumbing and a captured TUI-prompt wire format per vendor, neither built yet. Don't confuse this with the :interactive template above, which sidesteps the whole problem by handing the task to a brand-new native session instead of trying to relay one.
  • No cost/consent gate beyond the explicit flag itself — a delegated call can spend against a different subscription/API key than the one you're directly watching.
  • Delegation is not instant, and that's mostly not Glider. A delegated CLI pays its own full cold start — process launch, auth, model listing, then inference — on every call, because there's no persistent session to reuse. Measured standalone with Glider entirely out of the path, a trivial one-line cursor-agent task still takes ~20s. Budget accordingly for multi-step work. Glider imposes no time limit of its own on a delegated call — it ends when the vendor's own CLI finishes or times out, or when you abandon the request.
